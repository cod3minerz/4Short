# No dead UI

Client's standing rule, verbatim: "не допускаем тупорылых нарисованных нерабочих ui" — no drawn-but-non-functional UI elements. Every pixel must be deliberate and functional.

## The one rule

**A control either does something real, or it is a `LockedField`. There is no third option.**

Forbidden:
- A button with no `onClick`/`onPress`.
- A toggle whose state nothing reads (`captions`/`silence` switches that never reach `recompute()` was exactly this bug).
- A `<select>` with `defaultValue` and no `onChange`, wired to a request that hardcodes its own values regardless of what's selected.
- A feature card that looks purchasable but has no provider, no job type, no debit behind it (AI B-roll/music before F-phase backend work lands).
- A "coming soon" badge on a control that still LOOKS clickable and enabled.
- An icon that visually promises a SEPARATE action (a `MoreHorizontal`/"…" implying a context menu, a chevron implying expand) sitting inside a bigger clickable element whose own `onClick` does something else entirely. Found live in `styles-view.tsx`: each style row was one `<button onClick={() => setActiveOverride(...)}>` with a `<MoreHorizontal>` rendered as a plain trailing icon, no `onClick` of its own, no menu anywhere in the tree — clicking the dots did the exact same thing as clicking the row's title. This is dead UI even though the row AS A WHOLE is functional, because the icon is a promise the code never keeps. The accessibility tree gives this away fast: `read_page` shows the whole card as a single button with no distinct child button for the icon — if a "…"/chevron/overflow icon doesn't get its own `button`/`ref` in that tree, it's decorative, not functional. Fix: remove the icon (if the action it implied is unbuilt and no product ask exists for it) rather than leaving a promise with nothing behind it.
- A visible button whose visual anatomy is copied from a working HeroUI compound component (e.g. `<button slot="trigger">` instead of `Disclosure.Trigger`) — see `dashboard-design-system` skill's HeroUI section. It looks identical, keyboard-focuses fine, but never registers the library's press handling, so every click silently no-ops. Found in `PanelSection.tsx`: all 8 accordion sections in the clip editor's right panel were stuck at their default expand state — especially bad since 5 default to collapsed, making their settings unreachable. This is the same failure mode as a missing `onClick`, just harder to spot by reading the JSX (it LOOKS wired) — verify by checking real DOM state (`data-expanded` or equivalent) before/after a real click, not by reading the component tree.
- A link/nav item shown to every user that only works for a privileged subset (found: `dashboard-shell.tsx`'s profile menu unconditionally linked every signed-in user to `/admin`, which has zero client-side route guard and relies entirely on API-level `adminOnly` checks — the dashboard session has no admin/role flag to gate the link with, so it was removed rather than left showing a page most users can't actually use). If a nav item needs a capability the current session data can't express, that's a sign it needs either a real capability check added first, or it shouldn't be in the universally-shown nav at all.
- A mutation that optimistically flips visible state before the network call resolves, with no rollback and no error message if the call fails — the UI ends up lying about what the server actually has. Found in `styles-view.tsx`/`store.ts` (E-AUDIT): clicking "Использовать по умолчанию" called `setDefaultStyle(id)`, which immediately marked the clicked style as default in local state (checkmark badge flips instantly) and only THEN called the real `saveStyle` PATCH — `void setDefaultStyle(...)` at the call site had no `.catch` at all, so a failed save left the wrong style permanently showing "Стиль по умолчанию" in the UI with nothing ever telling the user the change didn't persist. The sibling "Сохранить изменения" button had a `catch` block, but it only did `setSaved(false)` — silently reverting a checkmark icon with no visible message, same practical result. Both are the same failure shape as a 200-response-but-not-persisted bug (see `backend-capability-map`'s "layoutOverride" entry), just triggered by a rejected promise instead of a lying response. Fixed by making `setDefaultStyle` roll back `defaultStyleId`/`isDefault`/`dirty` to their pre-optimistic values on failure (still rethrowing so the caller's message shows), and adding a local `saveError` state in `styles-view.tsx` rendered next to the footer buttons for both actions. Check for this pattern wherever a `void someAsyncCall()` fire-and-forget appears at a JSX call site with no accompanying `.catch`/`try` — it means failures are unhandled promise rejections by construction, not just under-messaged. Same pass found a second, milder instance in `dashboard-shell.tsx`'s `handleSignOut` — its `catch { setSigningOut(false) }` reverted the spinner with no message on a failed sign-out, silently leaving the user on the page with no explanation. Fixed the same way: capture `error` and render it (`signOutError`) in the profile popover next to the button.

**A "friendly" error message can still be a lie if it forwards the wrong error's text.** Found only by running a real local backend end-to-end (Postgres + control-api, not preview mode) and triggering a genuine network-layer failure: 23 catch blocks across 6 files (`project-workspace.tsx`, `clip-editor.tsx`, `styles-view.tsx`, `dashboard-shell.tsx`, `account-view.tsx`, `store.ts`) used the pattern `error instanceof Error ? error.message : "<Russian fallback>"`. `ControlApiError` (the app's own error class, thrown by `request()` in `control-api.ts`) IS an `Error` subclass with a real, server-authored, already-Russian message — but so is a bare `TypeError` from a failed native `fetch()` (offline, DNS failure, CORS misconfig, server unreachable), whose `.message` is a raw English browser string like `"Failed to fetch"`. Checking `instanceof Error` can't tell these apart, so any pure network failure showed English browser internals to Russian-speaking users instead of the intended fallback message — the exact opposite of what the fallback branch was written for. Reproduced live: a `PUT /v1/styles/:id` failing at the network level (`net::ERR_FAILED`, no request ever reaching the server despite a successful CORS preflight) rendered literally "Failed to fetch" in the style editor's footer. Root-caused the PUT failure itself afterward: it wasn't a 4Short bug — every PUT request failed identically in that specific browser-automation session regardless of target (even a nonexistent path), while GET/POST/OPTIONS all worked fine, meaning something in that tool's own request layer was blocking the PUT method universally. The underlying network failure was an artifact of the testing tool, but the raw-English-message leak it exposed is real and was already live in the codebase — any genuine network hiccup (WiFi drop, DNS failure, corporate proxy) would trigger the exact same user-facing bug for real users, on any HTTP method. Only 3 of the original 26 call sites (`billing-view.tsx` purchase, `new-project-wizard.tsx` `verifyUrl`/`launchProject`) already used the correct, narrower `error instanceof ControlApiError` check — those three happened to be the highest-stakes money/creation actions, suggesting the narrower check was a deliberate choice there but never propagated to the rest of the codebase. Fixed by switching every site to `instanceof ControlApiError`, so only real server-authored messages ever reach the user; anything else (network failure, unexpected exception) now falls through to the honest, already-existing Russian fallback text. **Grep before adding any new catch block**: `grep -rn "instanceof Error ? .*\.message" app/dashboard/` should always return nothing — if it does, that site will leak raw browser/JS errors the moment a real network failure happens, which preview-mode testing can never trigger and code reading rarely catches (the bug looks identical to the correct pattern until you read the type annotation closely).

Required instead: `app/dashboard/components/ui/LockedField.tsx` (build if missing) — visibly disabled, a lock icon, and a one-line reason (`"Скоро"`, `"На тарифе Эксперт и выше"`, `"Нужен трекинг лица — пока недоступно"`). The reason must be true, not generic.

## Before marking any page "done"

1. Click every control. Literally — via the browser tools, not by reading the JSX. If it's supposed to change something, confirm the change happened (state, network request, or visible DOM change).
2. For every value a user can set, trace it to where it's consumed. If the consumer ignores it (hardcodes something else, like `services/control-api/src/routes/projects.ts` recompute used to), that's the same class of bug as a dead button — fix the wiring or lock the control.
3. Cross-check against `backend-capability-map` (sibling skill) before building UI for anything that sounds like it needs AI generation, a new source platform, or per-clip persistence you haven't confirmed has a database column.
4. If unsure whether something is real, grep the backend yourself before writing the component — don't assume a plausible-sounding feature exists.

## Known current lock list (update as backend work lands)

As of this plan, these must render as `LockedField`, not as working controls, until the corresponding Phase F backend item ships:
- AI B-roll, AI music (no provider, no job type, no debit — `backend-capability-map`)
- Хук / opening text overlay (no schema field, nothing renders it)
- Custom watermark upload, custom outro upload (`brand_assets` table has zero references anywhere)
- 2K / 4K render quality (only 720p/1080p exist)
- Clip formats that require face tracking (`active_speaker`, two-person `two_speakers`) — `face_track` returns `FACE_MODEL_NOT_INSTALLED`
- Clip editor's "Спикер в кадре" select (`clip-editor.tsx`) — was a live-looking dropdown with fake names sourced from mock transcript data, but `state.speaker` was never included in `compileEdl()`'s payload at all; only meaningful once active-speaker tracking renders (same blocker as the layout modes above), so locked with the same reason.
- Clip editor's "Нормализовать звук" switch — toggled local state that `compileEdl()` never sent; no `normalize` field anywhere in `clipEdlSchema` or the render worker.
- Project workspace's per-moment "Кадр" select (`project-workspace.tsx`) — accepted by `updateMomentSchema` (`layoutOverride`) and returned 200 with no error, but `moment_candidates` has no column for it and the PATCH handler never wrote it; the change looked saved and silently reverted on reload. Caught by a fresh review agent, not by the original build — a 200 response with a schema-validated body is not proof a field is persisted, only a route+column write is (see `backend-capability-map`'s verification method).
- Wizard cutting modes `uniform` ("Простая") and `manual` ("Один фрагмент") — `find_moments` (`services/media-worker/src/fourshort_worker/stages.py:156-175`) has zero mode branching; every mode runs the identical AI candidate-search + rerank prompt. Selecting "Простая" or "Один фрагмент" silently ran AI search anyway while claiming even segments / one exact fragment — worse than a dead button, since it's a live selector whose selected value is thrown away. Locked in `new-project-wizard.tsx` (E-AUDIT pass) until the worker gets real per-mode logic (uniform: synthesize evenly-spaced segments without calling the LLM; manual: synthesize one moment directly from `sourceRange`, no AI search at all).
