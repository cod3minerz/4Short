# Backend capability map

Read this before designing UI for a feature. It exists because the previous redesign pass built wizard/editor UI for several things that were never wired to any backend — the failure mode this skill prevents.

**This file goes stale.** Whenever you change a route, a worker stage, or a contract, update the relevant row here in the same change.

## The most severe finding so far: no frontend code ever provisioned a workspace

Every authenticated `control-api` route requires an `X-Workspace-Id` header (`requireWorkspace` in `services/control-api/src/plugins/context.ts` throws a hard 400 if it's missing — no auto-resolution, no "use the user's only workspace" fallback). The dashboard reads that header's value from `localStorage` via `getWorkspaceId()`/`setWorkspaceId()` (`app/dashboard/lib/control-api.ts`). A real, complete backend endpoint already existed to create one — `POST /v1/onboarding/workspace` (`services/control-api/src/routes/onboarding.ts`), which seeds free-trial minutes and a default style — but **`setWorkspaceId()` was never called anywhere in `app/**`, and nothing ever called the onboarding route either.** In any real, connected deployment, a brand-new user could sign in successfully (auth works fine) and then every single subsequent API call — billing, projects, styles, everything — would fail with a 400, because no workspace ID was ever stored. This is more severe than any single-page bug found this session: it would make the entire product unusable for every real user, at the very first step.

Fixed (E-AUDIT) by: (1) making `POST /v1/onboarding/workspace` idempotent by user, not just by client-supplied idempotency key — it now looks up an existing `workspaceMembers` row for the signed-in user first, and only falls through to creating a new workspace if none exists, so a returning user (new device, cleared storage) lands back on their own workspace instead of getting a disconnected duplicate; (2) `ensureWorkspace()` added to `control-api.ts`; (3) `store.ts`'s `hydrate()` now resolves the session first (on its own, not in the `Promise.all`), and if there's a real signed-in user with no stored workspace ID, calls `ensureWorkspace()` and `setWorkspaceId()` *before* running any of the workspace-scoped fetches; (4) `signOut()` now clears the stored workspace ID too, so a second user signing in on the same browser doesn't inherit the first user's (inaccessible) workspace. If you touch workspace resolution again, re-verify this chain end-to-end — it can't be exercised in this repo's disconnected dev preview (`isControlApiConfigured()` is false here), so it was verified by tracing the code against `services/control-api/src/plugins/context.ts`, `tsc`, `next build`, and the backend's own `tsc`, not by a live click-through.

### A second, deeper part of the same gap: there was no sign-in UI anywhere

Even with workspace provisioning fixed, nothing in `app/**` ever triggered a sign-in — no email/OTP form, no OAuth button, `getSession()`/`signOut()` were the only auth-related frontend code, both of which just assume a session already exists. The backend (`services/control-api/src/auth/index.ts`) is fully configured for real email-OTP sign-in via `better-auth`'s `emailOTP` plugin (`emailAndPassword` is explicitly disabled) plus optional Yandex OAuth — but nothing called it. Fixed (E-AUDIT) by adding a real sign-in page at `app/sign-in` (deliberately **outside** `app/dashboard/**`, as a new top-level route, so it isn't wrapped in `DashboardShell` and doesn't touch `app/page.tsx`/`app/components/*`):
- `app/sign-in/page.tsx` + `sign-in.css` — a two-step email → OTP-code form. Calls `sendSignInOtp`/`verifySignInOtp` (new in `control-api.ts`), hitting `POST /v1/auth/email-otp/send-verification-otp` and `POST /v1/auth/sign-in/email-otp` — real endpoint paths and body shapes, confirmed by reading `node_modules/better-auth/dist/plugins/email-otp/routes.mjs` directly rather than guessing. On success, redirects to `/dashboard` (or a `?redirect=` target), where the newly-fixed `hydrate()` picks up the fresh session and provisions the workspace automatically.
- **Yandex OAuth is intentionally not wired** — it's conditionally configured server-side (`YANDEX_CLIENT_ID`/`YANDEX_CLIENT_SECRET`) and the frontend has no way to know if it's actually enabled without a new endpoint; email-OTP alone fully closes the "nobody can sign in at all" gap, so this was left as a known, smaller remaining item rather than scope-creeping further.
- `dashboard-shell.tsx` now redirects to `/sign-in?redirect=<path>` when `connection === "connected" && !user` — i.e. only once the real backend has actually answered and confirmed there's no session; the `connection === "preview"` (API not configured) state never redirects, since that's a deliberate offline-demo mode, not a signed-out one.
- None of this is exercisable live in this repo's disconnected dev preview; verified via `tsc`, `eslint`, `next build`, and reading the real better-auth plugin source for exact contracts.

**Caught by a fresh review agent, not by me: the sign-in fix above shipped with a redirect loop that would have made it completely unusable.** `store.ts`'s `hydrate()` is guarded by a module-level `hydrated` flag set `true` before the first `await` and *never reset*. The redirect-to-sign-in itself (in `dashboard-shell.tsx`) is what triggers the first hydration, permanently caching `user: null`. After a real user completed the OTP flow, `router.push("/dashboard")` (a soft navigation) didn't reload the module, so `hydrate()` no-opped on the stale `hydrated=true`, the store kept reporting `user: null`, and the redirect fired again — sending a just-authenticated user straight back to `/sign-in`. `signOut()` already avoided this exact trap by using `window.location.href` (a hard reload, which does reset module state) instead of a router push — that asymmetry is what hid the bug from a sign-out-only test. Fixed by making the post-verify redirect in `app/sign-in/page.tsx` a hard navigation too (`window.location.href`, not `router.push`). **Lesson for next time:** any code path that changes what `getSession()`/`getWorkspaceId()` would return must navigate with a hard reload, not `router.push`/`router.replace` — the dashboard store's hydration is a one-shot-per-page-load singleton by design (mirrors `styles`/`billing`/`projects`, all fetched once and cached), so client-side navigation across an auth-state change will always see stale data.

**Also caught in the same pass, pre-existing (not something this session's other changes introduced):** the per-moment "Кадр" override in `project-workspace.tsx`'s moment inspector (a raw `<select>`, not using the shared `Select`/`LockedField` primitives) called `updateMoment(..., { layoutOverride: {...} })`. `updateMomentSchema` (`packages/contracts/src/api.ts`) accepts and validates `layoutOverride` and `speakerId`, the request returned 200 with no error — but `momentCandidates` (`db/schema.ts`) has no column for either field, and the PATCH handler (`services/control-api/src/routes/projects.ts`) never wrote them. The UI showed the change as saved; on reload it silently reverted, because the API-moments mapping in the same file hardcodes `layout: "auto"` for every moment regardless of what was picked. Fixed by locking the control (`LockedField`, "Свой формат для отдельного момента — пока недоступно, используется формат проекта") and removing the now-dead `layoutOverride` plumbing from `updateActive()`/the `layouts` option list, rather than attempting a schema migration to actually persist it — that's a real data-model change (new columns + a `db:generate`/`db:migrate` this sandbox has no live database to verify against), out of proportion for this pass. `speakerId` on the same schema has the identical "accepted, nowhere to store it" gap but was never actually reachable from any UI control, so it wasn't touched.

**Small adjacent fix, found while verifying the above:** `services/control-api/src/app.ts`'s CORS `allowedHeaders` list was missing `X-Development-User-Id` — the exact header the frontend sends (and `plugins/context.ts` + `routes/onboarding.ts` read) for the local dev-mode auth bypass (`NEXT_PUBLIC_DEVELOPMENT_USER_ID`). Since the dashboard's default dev ports differ from the API's (`:3000`/`:3001` vs `:4100`), this is a real cross-origin request and the browser's CORS preflight would have silently stripped/blocked the header, making the dev-user-id bypass non-functional whenever frontend and backend run on different origins — which is the default setup. Added to the allowlist.

## Critical: `transcript_segments` was never written at all — the transcript feature had zero real data

Found while reading `app/dashboard/lib/transcript.ts`'s `toEditorWords()` — its own comment already flagged "nothing in this repo writes it yet" for the `.words` column, which prompted checking one level up: does anything write `transcript_segments` *rows* at all? It didn't. `pipeline.ts`'s `speech_to_text` completion handler wrote the raw STT provider response into `transcripts.originalPayload` (an opaque jsonb blob) and stopped there — nothing ever parsed it into `transcript_segments` (ordinal/speakerId/startMs/endMs/originalText/words). `GET /v1/projects/:id/transcript` does a plain `select from transcript_segments where transcriptId = ...` with no fallback, so for every real, connected project this always returned an empty array. That silently broke: the clip editor's transcript panel, `project-workspace.tsx`'s transcript drawer (both fixed earlier this pass to *use* real segments once fetched — this is the reason there was nothing to fetch), word-level editing (`toEditorWords`), and by extension `transcript_revisions`' hide/cut/replace-word operations (already documented above as write-only/never-replayed — now clear that was compounding on top of segments that were never there to begin with).

Fixed for one of the two configured STT providers: `services/control-api/src/services/transcript.ts` (`parseSttResponse`) parses the OpenAI-Whisper `verbose_json` shape (`OpenAICompatibleStt` in the worker) — a stable, well-documented format — into segment rows, bucketing any top-level `words[]` timings into their containing segment by time range. Wired into `pipeline.ts`'s `speech_to_text` handler (delete-then-reinsert on each transcription). **Deliberately not fixed for `YandexSpeechKit`, and — important — `yandex_speechkit` is the worker's DEFAULT `stt_provider`** (`services/media-worker/src/fourshort_worker/config.py:34`), not a rare alternate path. Its async-recognition response is a materially different, more deeply-nested shape (per-channel/per-chunk alternatives) that this pass could not verify against a live response or any fixture in the repo — guessing at the field names risked silently writing *wrong* segments to a real database, which is worse than the current empty state (wrong data actively misleads a user editing their transcript; empty data is at least honestly absent and the existing empty-state UI handles it). **This means the fix above only takes effect if a deployment explicitly overrides `STT_PROVIDER=compatible`** — on the default config, `transcript_segments` is still never populated. Whoever picks this up next should get one real Yandex SpeechKit v3 `recognizeFileAsync` response (either from a live call or Yandex's own API reference) and extend `parseSttResponse` in `services/control-api/src/services/transcript.ts` with a second branch for it, verified against that real shape rather than assumed. Real unit tests added: `tests/unit/stt-transcript-parsing.test.ts`.

## A systematic sweep of every request-body schema (E-AUDIT), after the moment-layoutOverride finding above turned out not to be isolated

Prompted by the `updateMomentSchema.layoutOverride`/`speakerId` finding (a field validated, accepted, 200-returned, but never written to any column), a background agent traced every request-body zod schema in `packages/contracts/src/*.ts` to its route handler(s) and downstream consumers, looking for the same "silently inert" pattern. Two more found:

- **`createProjectSchema.projectOverrides` — real bug, fixed.** The wizard's format-picker step sends this (`new-project-wizard.tsx`: `projectOverrides: { layout: layoutToApi(layout) }`), meaning **every project's per-project format choice from the wizard was being silently ignored at render time** — `services/control-api/src/services/pipeline.ts`'s `find_moments`→`face_track` handler built the EDL purely from `clip.style.config`, never merging in the project's stored `projectVersions.settings.projectOverrides`. The value *was* being written to a real column (so it's a step removed from a pure schema-only ghost field), just never read back — functionally identical to data loss from the user's point of view: pick "Размытый фон" in the wizard, every clip renders with whatever the linked *style's* layout says instead. Fixed by fetching the project's current `projectVersions.settings.projectOverrides` in the `face_track` handler and shallow-merging it over the style config before building the EDL (shallow merge is correct for the one field ever actually sent — `layout` — don't extend to a deep merge without a second field in real use to verify against).
- **`createMomentSearchSchema.resultMode` — confirmed real gap, left undone.** `"replace"` is meant to clear prior search results before inserting new ones; nothing in `pipeline.ts`'s `find_moments` completion handler branches on it at all — old `moment_candidates` from earlier searches always remain selectable regardless of which value is sent. **Currently unreachable in practice**: the only real call site (`project-workspace.tsx`'s `recompute()` / "Найти иначе") always sends `resultMode: "append"`; `"replace"` is never actually requested by any UI flow today. Not fixed — implementing real replace semantics needs a product decision this pass can't make blind (delete old `moment_candidates` outright vs. soft-hide vs. deselect; `clips.momentCandidateId` is `onDelete: "set null"` so a hard delete wouldn't destroy already-rendered clips, but would orphan their moment reference) and there's no live UI path to verify a fix against, unlike the `projectOverrides` case above. If a "replace"-triggering control is ever added to the UI, implement this then, with that real call site's exact intent to build against.

Two other schemas were checked and are genuinely unreachable/unfinished rather than broken, not urgent: `generativeQuoteSchema`/`confirmGenerativeOperationSchema` are defined but **no route parses either one at all** — `generative_operations`/`generative_balance_transactions` tables exist with zero API surface, consistent with AI B-roll/music being fully absent per the row below. Everything else checked out clean (`updateProjectSchema`, `createTranscriptRevisionSchema`, `updateClipSchema`, `reserveMinutesSchema`, style/upload/admin/job schemas).

| Projects list ("Мои проекты" page) | **Was 100% hardcoded mock data** — `projects-view.tsx` imported the static `projects` array from `data.ts` directly and never called the backend at all, even though `GET /v1/projects` was already real and working. | Sign-in redirect for a genuinely signed-out visitor | **Was unreachable in practice** — `dashboard-shell.tsx`'s redirect-to-`/sign-in` effect only fired on `connection === "connected" && !user`. But a real signed-out visitor hitting a protected dashboard page causes `listStyles`/`getBillingSummary`/`listProjects` (all workspace-gated) to 401, which lands `hydrate()`'s `catch` block and sets `connection: "error"` — never `"connected"`. So the exact case this redirect exists for never satisfied its own condition: a real signed-out user landed on an honest-but-dead-end "API недоступен / Authentication required" empty page forever, with no visible link to `/sign-in` anywhere in the shell. Only caught by running a real local backend (Postgres + control-api) end-to-end in the browser — signing out and revisiting `/dashboard/projects` reproduced it immediately; it was invisible to code reading and to preview-mode testing, since preview mode never reaches `connection: "error"` at all. Fixed two ways together: (1) `store.ts`'s `hydrate()` now resolves `getSession()` and derives `user` BEFORE the try/catch, so a later failure in the workspace-scoped `Promise.all` can't erase a real signed-in identity into `user: null` — this matters because `connection: "error"` can also mean a transient 500/network blip for a REAL signed-in user, who must not be bounced to sign-in; (2) the redirect effect now checks `connection === "connected" || connection === "error"`, both gated on the now-reliable `!user`. Verified live: real OTP sign-in → real 201 `POST /v1/onboarding/workspace` → sign-out → revisit a protected page → correct redirect to `/sign-in?redirect=...` → fresh OTP → lands back on the originally-requested page, not just `/dashboard` | `app/dashboard/store.ts` `hydrate()`, `app/dashboard/components/dashboard-shell.tsx` redirect effect |
| Projects/styles pages on a real connection error (not preview) | **Was silently showing the fake demo dataset** — `hydrate()`'s catch block did `replace({ ...serverState, connection: "error", ... })`; `serverState.projects`/`.styles` are the SAME mock arrays used for the deliberate offline "preview" case (API not configured at all). Verified live against a real backend by triggering an actual 401 (no session) | `app/dashboard/store.ts` `hydrate()` catch branch, `app/dashboard/components/styles-view.tsx` empty-state guard |
| New-project processing screen's stage mapping | **Was showing the wrong stage from the moment a project is created** — only found by actually creating a real project against a live backend and reading the real `projects`/`jobs` rows. Verified live twice: before the fix, a fresh project showed "Этап 2 из 4"; after, the same flow showed "Этап 1 из 3" — correct | `app/dashboard/components/new-project-wizard.tsx` `processingStages`/`stageByStatus`, `services/control-api/src/services/pipeline.ts` `advancePipeline` |
| Project workspace's "Моменты" tab for a real, not-yet-processed project | **Probably the single worst finding of the entire E-AUDIT pass** — `project-workspace.tsx`'s `items` state was initialized to the mock `demoMoments` array, and the load effect only overwrote it with real data `if (apiMoments.length)`. A brand-new or still-processing real project genuinely has zero real moments — that's not an edge case, it's the normal state for the first several minutes of every project's life. ## How to re-verify a row yourself

```bash
# Does a route exist for X?
grep -rn "X" services/control-api/src/routes/

# Does the worker actually consume a config field, or silently ignore it?
grep -n "field_name" services/media-worker/src/fourshort_worker/*.py

# Is a DB column ever written, or only read?
grep -rn "column_name:" services/control-api/src/routes/
```

Never take a type definition, a UI mock (`data.ts`), or a schema field as proof a feature works — schemas describe intent; only routes, worker code, and actual writes prove reality.
