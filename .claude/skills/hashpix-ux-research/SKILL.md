# Hashpix UX Research

Research the market to improve decisions, not to assemble a visual moodboard.

## Investigation method

1. Name the user, job, context and irreversible decision being studied.
2. Gather primary product evidence: live product screens supplied by the user,
   official docs, pricing, release notes, help centres and public changelogs.
   Mark screenshots as observed behaviour, not proof of backend capability.
3. Trace one complete task: entry, decision points, state changes, errors,
   waiting, undo/recovery and result.
4. Separate observed fact, inference and recommendation.
5. Compare each mechanism against HVE constraints, current API capability,
   mobile ergonomics, cost and operational risk.

## Required deliverable

Write a decision table with: user job, competing pattern, benefit, failure or
dark pattern, Hashpix adaptation, technical dependency, and verification.

Finish with exactly three lists:

- adopt now — improves a current, supported workflow;
- prepare in architecture — valuable but depends on HVE/API work;
- reject — creates cost, deception, UI noise or editor complexity.

## Editor research lens

For professional editors, evaluate information hierarchy before appearance:

- where the source truth lives (transcript, scenes, or timeline);
- how selection determines editable properties;
- what is global, project-scoped and clip-scoped;
- how a user discovers and undoes a change;
- whether preview and final render are truthful;
- how the workflow contracts on tablet/mobile.

Prefer a single focused work surface plus contextual tools. Do not import a
multi-track timeline or generative feature just because a competitor shows it.

## Evidence rules

- Use web research for unstable pricing, current capabilities or release facts.
- Cite the direct authoritative URL next to each factual claim.
- Do not claim that a competitor's visible control is functional without a
  documented or exercised workflow.
- Do not use made-up performance, conversion, quality or engagement metrics.
