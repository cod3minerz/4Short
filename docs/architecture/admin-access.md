# Platform admin access

Права платформы и права внутри workspace — разные уровни.

## Платформенные роли

- `user` — обычный пользователь, доступа к `/v1/admin/*` нет.
- `support` — только чтение пользователей, аккаунтов, очереди и журнала.
- `admin` — блокировка пользователей, тарифы, минуты, retry/cancel задач.
- `super_admin` — всё перечисленное и назначение платформенных ролей.

Роли `owner/admin/member` в `workspace_members` относятся только к конкретному
аккаунту клиента и не дают доступ к административному API.

## Первый super admin

До появления первого сохранённого администратора используется
`PLATFORM_ADMIN_EMAILS`. Это comma-separated allowlist подтверждённых email.
Пользователь из списка получает эффективную роль `super_admin` после обычной
авторизации. Все остальные роли сохраняются в `users.platform_role`.

Allowlist не заменяет авторизацию и не создаёт пользователя. В production он
должен содержать только владельцев платформы.

## Защита

- Все `/v1/admin/*` маршруты проходят `requirePlatformAdmin`.
- Заблокированный пользователь теряет доступ и к кабинету, и к admin API.
- Нельзя изменить собственную роль или заблокировать самого себя.
- Обычный `admin` не управляет ролями и не блокирует других администраторов.
- Коррекция минут использует append-only ledger и требует `Idempotency-Key`.
- Каждая мутация записывается в `audit_events`.
- UI не содержит mock-режима: без Control API показывается закрытое состояние.
